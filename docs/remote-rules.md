# 解析规则远程下发：评估和设计

> 2026-11 写。对应路线图 9.5 的“解析规则远程下发”。更新签名密钥（D1）已经配好，所以这一项现在可以做；这份文档回答两个问题：值不值得现在做，做的话怎么做。

## 一、要解决的问题

平台改版（接口地址、页面里数据的位置、链接格式变了）以后，解析就失效，现在只能发一个完整版本才能修。想法是把“会变的那一小部分”做成签名的规则包，程序自己去拿，不用等发版。

## 二、证据：最近的解析问题，有几个只靠规则能修好

我翻了 `providers/` 目录的提交历史和最近报上来的问题。**一个问题都不是“网站改了一个字段”这一类：**

| 问题 | 实际原因 | 规则能修吗 |
|---|---|---|
| B站创作者主页解析不了 | 没写这个功能（只支持单个视频） | 不能，要写代码 |
| YouTube 播放列表展不开 | 没写这个功能 | 不能 |
| 屏幕翻译点了没反应 | WebView2 运行时被系统更新后断开 | 不能，和解析无关 |
| 订阅 B站合集订的是全部投稿 | 订阅逻辑的取法错了 | 不能，要改代码 |
| 无字幕视频、字幕读取失败 | 字幕获取流程和重试策略 | 不能 |

`providers/` 目录从 0.5.1 到现在一共 18 个提交，几乎都是新功能（新平台、新页面类型、新协议），没有一条提交的内容是“抖音 / 小红书 / 快手改了页面结构，调整一个路径或正则”。

**要注意这个结论的局限：**

- 仓库里没有 Issue，也没有解析失败的统计，所以上面是“能从提交历史和对话里看到的”，不是完整数据。
- 现在的测试样本是手写的（见 `tests/fixtures/`），没有真实响应，所以平台“悄悄改版”的失败也许发生过但没有被发现。
- 抖音、快手、小红书、微博用隐藏窗口读页面，这几个最容易被改版打断，也最需要真机验证；这是规则下发最可能有用的地方，但我现在没有真机上的失败记录。

## 三、如果做，能放进规则包的和不能放的

**可以（数据，不是代码）：**

- 各平台的链接识别正则（`classify`、`matches`）。
- 页面里数据所在的位置：`<script>` 里的变量名、JSON 里的字段路径（比如抖音 `aweme_detail.video.play_addr.url_list[0]`）。
- 接口地址和参数模板（B站的 `x/web-interface/view`、`x/space/wbi/arc/search` 等）、必须带的请求头。
- 隐藏窗口里“点哪里、等哪个元素”的选择器。

**不能：**

- 任何会执行的脚本。规则只能在程序里已有的几种取法里选择和调参，不能加新取法；新取法仍然要发版。这样规则包被篡改或写错，最坏的结果是解析失败，不会执行任意代码。
- 下载、合并、后处理的逻辑。

## 四、设计

1. **格式**：一个 JSON：`{ version, minApp, issuedAt, rules: [ { platform, kind, pattern / path / url, … } ] }`。`minApp` 低于当前程序版本才生效（以后程序里加了新取法，旧规则不会误用）。
2. **签名**：用 Ed25519（minisign 格式，和更新签名同一套工具 `tauri signer sign`）。**建议用一把单独的密钥**：更新密钥丢了或泄露后果是“能给所有用户推任意安装包”，规则密钥的后果小得多，不应该共用。公钥编译进程序，私钥放在仓库 Secret。
3. **发布**：`rules.json` 和 `rules.json.sig` 作为一个固定名字的 Release 资源，程序从 `releases/download/rules/…` 取（专门一个名叫 `rules` 的 Release，只更新资源，不发版）。不需要服务器。
4. **使用**：程序每天最多检查一次（设置里可以关），验签通过、`minApp` 合适、**并且规则包里自带的样本测试通过**才启用；任何一步失败都回到程序内置的规则。上一个能用的规则包留在本地，网络不通时继续用。
5. **回滚**：发一个新版本号更低的覆盖不可行（版本只升不降），所以规则包里有 `revoke: [版本号…]`，程序见到就丢掉那些版本缓存的规则。
6. **可见性**：设置里的“平台健康检查”和诊断信息里写上当前规则包的版本；检查失败的平台能一眼看出是内置规则还是下发规则出的问题。
7. **改动量**：6 个内置平台（抖音、快手、小红书、B站、微博、Pixiv）的解析代码要把“会变的常量”改成从一张规则表里取（表里默认值就是现在写死的值）；加一个签名脚本和一个发布工作流；加设置开关。大约是“中到大”，主要的风险在重构每个平台时不要改变它现在的行为，所以要先有真实响应样本（见 `docs/` 里的真实样本导入脚本）。

## 五、我的建议：现在不做，先做两件准备工作

1. **先攒真实样本**：打开“录制样本”，把几个平台的主页、单个作品、列表页各录几份，用 `scripts/import-sample.mjs` 导入。没有它们，重构解析代码去读规则表时没有办法验证行为没变。
2. **再观察一到两个版本**：每次发版后跑“平台健康检查”并把结果发给我（也可以只发“复制结果”的内容），记录每次失败的原因。如果以后的失败里有三分之一以上是“改版导致的字段变化”，就按上面的设计做；如果大部分仍然是“缺功能”，规则下发的收益很小，不值得为它增加签名、发布和回滚的复杂度。

做规则下发之前，**你需要做的**只有一件：确认要不要再单独生成一把规则签名密钥（步骤和更新密钥一样，名字不同，我再写一份配置说明）。

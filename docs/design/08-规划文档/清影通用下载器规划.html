清影通用下载器规划

对当前桌面程序（Rust 约 3500 行 + Vue 前端）的审查结果，以及改造成“通用下载器 + 国内平台专项支持”的方案。本页只做规划，没有改动代码。

结论已确定的决定审查发现方案对比目标架构账号与 Cookie断点续传网络与下载源短剧与剧集订阅与追更直播录制手机发链接功能清单平台细分分阶段计划质量与维护

结论：建议重构，但分阶段演进，不推倒重写。

做法是“通用内核 + 平台插件”：五个国内平台保留现在的原生解析器，另新增 Pixiv 原生插件（yt-dlp 在这些平台上不支持、支持不全或经常失效）；其他网站交给 yt-dlp 兜底；再加上任意直链、m3u8（HLS）下载和 ffmpeg 合并。很多短剧和小站用 m3u8 播放，这一项对“短剧”场景帮助最大。

现有代码可以大部分保留：解析器、命名、数据库、界面结构都能复用。要改的核心是数据模型（从“一个作品几条直链”改为“作品 + 多种清晰度/格式 + 播放列表”）和下载任务（从内存里的单次 HTTP 下载改为可持久化、多步骤的任务）。

当前的合并请求 #1 已合并。完整计划约 24–27 周，分 7 个阶段：阶段 4 结束发布 1.0（通用下载器 + 手机发送），之后 1.1 加订阅追更、1.2 加直播录制。下一步从阶段 1“加固现有程序”开始。

已确定的决定

通用范围暂时只做视频和图片网站，不做任意文件、磁力、BT 下载。平台细分覆盖 yt-dlp 支持的全部站点（见第 12 节）。
yt-dlp 和 ffmpeg第一次用到时再下载，不打包进安装包。ffmpeg 选 LGPL 版本。
合并请求顺序#1 已于 2026-10-04 合并，重构按阶段另开合并请求。
新增三大功能订阅与追更（第 8 节）、直播录制（第 9 节）、手机发链接到电脑（第 10 节）都做，分别在 1.1、1.2、1.0 版本交付。
网络与短剧按网站分流（国内直连、海外走代理）、组件国内镜像（第 6 节）；短剧按集批量下载，加密短剧不支持（第 7 节）。
断点续传所有下载方式都必须支持，包括关闭程序、断网、直链过期之后继续下载（见第 5 节）。
Cookie 来源提供浏览器扩展同步、内置登录窗口、导入 cookies.txt / 手动粘贴三种。不做“从本机浏览器直接读取”（新版浏览器加密后成功率接近 0）。
“P站”同时支持 Pixiv 和 Pornhub，默认文案与示例以 Pornhub 为主。Pornhub 通过 yt-dlp 接入；yt-dlp 没有 Pixiv 提取器，Pixiv 做成原生插件。

1. 审查发现

按影响排序。位置为 desktop/src-tauri/src/ 下的文件。

级别问题位置影响与修法
高五个平台的解析都没用真实链接测过providers/*解析器可能一上线就失效。先在能访问这些网站的机器上逐个实测，并把真实响应保存为测试样本
高下载队列只存在内存里download.rs:69关闭程序或崩溃后，未完成任务全部丢失，.part 文件留在磁盘上。任务需要写入 SQLite，启动时恢复为“已暂停”
高数据模型只能表达“一条直链”model.rs:23、model.rs:78无法选清晰度，无法处理音视频分离（B站 1080P、YouTube）、m3u8 和合集。这是做通用下载器必须先改的地方
高没有日志和诊断信息全局用户反馈“解析失败”时无从排查。需要滚动日志文件，以及“复制诊断信息”按钮（版本、平台、脱敏后的请求与错误）
高登录 Cookie 明文写在 settings.jsonsettings.rs:35其他程序可直接读取账号凭据。改为加密存储，密钥放系统钥匙串（见第 4 节）
高下载文件时把平台登录 Cookie 发给了 CDNdownload.rs（按平台取 Cookie）例如 B站的登录 Cookie 会被发到 bilivideo.com 视频服务器。改为按域名匹配，Cookie 只发给它所属的网站
中Cookie 只存成一整串 name=value; …settings.rs、commands.rs丢失域名、路径、过期时间；微博的 .weibo.cn 和 .weibo.com 分不开，也无法提示过期。改为按条存完整字段
中B站播放地址接口没有做 wbi 签名，且只取 html5 合一 MP4providers/bilibili.rs可能被接口拒绝；只能拿到低清。需要 wbi 签名，高清走 DASH（视频轨 + 音频轨）再用 ffmpeg 合并
高直链过期重新解析后，已下载的部分被删掉从头下download.rs:241大文件下到一半链接过期，进度全部作废。重新解析后应先确认是同一文件（大小一致），再接着下
中续传时不校验服务器上的文件是否变了download.rs:473只发 Range，不带 If-Range，也不核对响应的 Content-Range 起点和总大小。文件被替换时会把两份内容拼在一起，得到损坏的文件
中同一资源可以重复加入队列download.rs:114只检查“已下载完成”的记录，不检查队列里正在下的同一资源，结果下载两份并生成“(1)”文件
中续传时速度显示瞬间虚高download.rs:205last_bytes 从 0 起算，续传后第一次计算把已下载部分当成本次速度。应从续传起点开始
中网络卡住时点“暂停”要等很久才生效download.rs:500只在收到下一块数据时检查暂停标记，最长要等 30 秒读取超时。应改为用取消令牌与读取操作同时等待
中文件名没有处理 Windows 保留名和路径长度naming.rs:83标题为 CON、NUL 等时保存失败；路径超过 260 字符时 Windows 上报错
中全局快捷键注册失败用户看不到commands.rs:78快捷键被其他软件占用时只打印到控制台。应返回错误并在设置页提示
中多数命令是同步命令，在主线程执行commands.rs（26 个命令中 3 个异步）数据库、删除文件等操作会短暂卡住界面，媒体库大了以后更明显。改为异步命令
中媒体库封面直接用平台 CDN 地址db.rs、媒体库页地址过期后封面全部不显示。下载时把封面缓存到本地
中没有代理和限速设置settings.rs需要代理的网站无法使用；下载时占满带宽。通用下载器必须有
低所有 t.cn 短链都被当成微博providers/weibo.rs指向其他网站的 t.cn 链接会报“没能识别微博 ID”。可先跳转，再按最终地址重新匹配平台
低只有中文界面前端做通用下载器后用户面更广，建议接入多语言

2. 要不要重构：三种方案

方案做法优点缺点结论
A. 保持专用只继续加国内平台解析器改动最小，安装包小每加一个网站都要自己写、自己维护；覆盖面永远有限不推荐
B. 通用内核 + 平台插件原生解析器优先，yt-dlp 兜底，再加通用直链 / m3u8 / 网页嗅探；统一的任务和后处理国内平台体验最好，同时覆盖上千个网站；yt-dlp 由社区维护需要管理 yt-dlp 和 ffmpeg 两个外部程序（体积、更新、许可证）推荐
C. 改成 yt-dlp 图形界面所有解析都交给 yt-dlp开发量最少yt-dlp 不支持快手，抖音、小红书经常失效；失去现有的差异化（同类产品已有 Open Video Downloader、Stacher 等）不推荐

路由规则：原生插件能匹配的链接先走原生，失败时再试 yt-dlp；原生匹配不到的交给 yt-dlp；yt-dlp 也不支持时做通用嗅探（判断是否直链、是否 m3u8，或在网页里找 <video>、og:video、.m3u8）。现有的远程 PHP 接口保留为抖音、快手的备用通道。

数据模型的主要变化

Media（作品）
├── 基本信息：平台、ID、标题、作者、封面、时长、发布时间、原始链接
├── formats：可选的清晰度 / 格式（列表）
│     每项：id、类型（视频 / 音频 / 音视频）、协议（http / hls / dash / ytdlp）、
│           分辨率、码率、编码、预估大小、请求头（Referer / Cookie / UA）
├── images：图集图片（列表）
├── extras：背景音乐、封面、字幕、弹幕
└── playlist：如果是合集 / 多 P / 用户主页，列出条目，按需再解析

Job（下载任务，存入 SQLite）
├── 选中的格式（视频轨 + 音频轨可分开）
├── 步骤：下载 → 合并 → 后处理 → 完成，每步都有状态和进度
└── 断点信息：已下载字节、分段进度、m3u8 已完成的分片

请求头从“按平台固定”改为“按资源携带”，这样 yt-dlp 返回的、需要特殊 Referer 的格式也能直接用内置下载器下载。

外部程序

  • yt-dlp：单文件可执行程序（约 20–35 MB），公有领域许可。建议首次需要时下载到应用数据目录，并支持在设置里一键更新，因为网站变化后通常要更新 yt-dlp 才能恢复。下载时校验 SHA-256。
  • ffmpeg：合并音视频、转封装、提取音频必需。体积较大（约 80 MB 以上），同样建议按需下载。要选 LGPL 版本，或者只下载不打包，避免整个程序受 GPL 约束。

4. 账号与 Cookie

YouTube、Pornhub、Pixiv、B站等网站的部分内容（年龄限制、会员专享、高清、R-18）需要登录才能下载。Cookie 做成一个统一模块，原生解析器和 yt-dlp 共用。

获取方式

方式适用说明
浏览器扩展一键同步（主力）所有网站，YouTube、Pornhub 首选在已登录的网页上点扩展按钮，扩展读取当前网站的 Cookie 发送给清影。不受浏览器加密影响。与“网页一键发送到清影”做成同一个扩展（Chrome / Edge / Firefox）
内置登录窗口（已有）B站、微博、国内平台、Pixiv谷歌会拦截内嵌浏览器登录，YouTube 不能用这种方式，界面上要直接引导到扩展
导入 cookies.txt / 手动粘贴兜底支持 Netscape 格式的 cookies.txt（与 yt-dlp 通用）和请求头里的 Cookie 字符串
从本机浏览器直接读取—不做。新版 Chrome 等浏览器在 Windows 上对 Cookie 做了专门加密，第三方程序成功率接近 0

存储与使用

  • 按条存完整字段：域名、路径、过期时间、Secure、HttpOnly。请求时按域名匹配，Cookie 只发给所属网站，不会再发给 CDN。
  • 加密存储：Cookie 文件用 AES-GCM 加密，密钥存系统钥匙串。不直接存进钥匙串，因为 Windows 凭据管理器单条约 2.5 KB，放不下 YouTube 的 Cookie。
  • 交给 yt-dlp：运行前生成只有当前用户可读的临时 cookies.txt，用 --cookies 传入，结束后把 yt-dlp 更新过的 Cookie 读回加密库，再删除临时文件。
  • 日志与诊断信息一律隐去 Cookie 值。

YouTube 的特殊处理

  • YouTube 会定期轮换 Cookie。导出的 Cookie 与浏览器里的会话同时使用时会很快失效，所以每次运行后都要读回 yt-dlp 更新后的 Cookie。
  • 引导用户按 yt-dlp 官方建议操作：用无痕 / 隐私窗口登录，同步 Cookie 后关闭该窗口，不再在浏览器里使用这次登录。
  • YouTube 有时还要求 PO Token 验证，光有 Cookie 不一定够。这部分依赖 yt-dlp 跟进，“一键更新 yt-dlp”必须做好。

界面与体验

  • 按网站显示登录状态：是否已登录、账号名（B站可通过个人信息接口取用户名和大会员状态）、关键 Cookie 过期时间（如 B站 SESSDATA、Pixiv PHPSESSID），以及“检测”按钮。
  • 出错时直接引导：解析返回“需要登录”“年龄限制”“会员专享”时，弹出“为这个网站添加 Cookie”，并按网站推荐获取方式（YouTube → 扩展）。
  • 同一网站多个账号：例如普通号和大会员号，下载时选择使用哪个。
  • 过期提醒：关键 Cookie 快过期时在设置页和托盘提示。
  • 保护账号：使用登录 Cookie 批量下载时自动降速、限数量，并提示登录后大量下载有封号风险。

边界

  • 只用于用户本人有权访问的内容（自己的会员权益、通过年龄验证的内容）。
  • 不做付费内容绕过和 DRM 破解；加密的会员剧集即使有 Cookie 也明确提示不支持。
  • 网站在某些地区因法规屏蔽访问时，程序不提供绕过手段。

5. 断点续传

目标：任何情况下中断，都从已下载的位置接着下，而且保证拼出来的文件完整、正确。

现在的情况

中断原因现在目标
手动暂停后继续支持（.part 文件 + Range 请求）保持；网络卡住时暂停也要立即生效
短暂断网支持，自动重试 3 次并续传重试次数和间隔可设置；网络恢复后自动继续
关闭程序、崩溃、断电、重启电脑不支持：队列在内存里，任务丢失，.part 变成孤立文件任务存数据库，启动后恢复，从 .part 的实际大小接着下
直链过期（403 / 404 / 410）会重新解析，但删掉已下载部分从头下重新解析后核对总大小，一致就接着下，不一致才从头
服务器上的文件被替换不检测，可能拼出损坏文件用 ETag / Last-Modified 检测，变化时从头下载并提示
服务器不支持 Range自动从头下载保持，并在任务上标注“不支持续传”
m3u8、音视频分离、yt-dlp 下载尚未实现按分片 / 分轨续传，合并失败不用重新下载

做法

  • 任务存数据库：每个任务记录地址、请求头、保存路径、.part 路径、总大小、ETag、Last-Modified、当前步骤（下载 / 合并 / 后处理）、各分段或分片的进度。每下载约 1 MB 或每 2 秒更新一次进度。
  • 启动时恢复：未完成的任务恢复为“已暂停”（可在设置里改成自动继续）；以 .part 文件的实际大小为准。发现不属于任何任务的 .part 文件时，提示用户清理。
  • 校验续传的是同一个文件：续传请求带 If-Range（优先 ETag，其次 Last-Modified）；收到 206 时核对 Content-Range 的起点等于本地已下载大小、总大小与记录一致；任何一项不符就从头下载。
  • 直链过期：重新解析拿到新地址后，先请求 1 个字节拿到总大小，与记录一致就保留 .part 接着下。抖音、B站等平台的视频地址几小时就过期，关机后第二天继续下载主要靠这一条。
  • 暂停立即生效：用取消令牌和读取操作同时等待，不再等下一块数据到达；暂停前把缓冲写入磁盘。
  • 分段多线程下载：先按总大小预分配文件，每段用 Range 下载并写到对应位置，数据库记录每段已完成的字节数；恢复时只补没下完的部分。服务器不支持 Range 时退回单线程。
  • m3u8（HLS）：分片单独保存到临时目录，数据库记录哪些分片已完成；恢复时只下缺的分片。播放列表地址过期时重新解析，按分片序号对应。加密密钥缓存下来。
  • 音视频分离（DASH）：视频轨、音频轨分别续传，都下完再合并；合并失败只重试合并。
  • yt-dlp 委托下载：使用 yt-dlp 自带的续传（保留它的 .part 文件，使用固定的临时文件名），恢复时用同样的参数重新运行。
  • 完成后校验：核对最终文件大小等于总大小；服务器提供校验值时一并核对；通过后再把 .part 改名为正式文件。

界面

  • 任务上显示“可续传”或“服务器不支持续传”；恢复时提示“已从 312 MB 处继续”。
  • 设置项：启动时自动继续未完成任务、重试次数和间隔、取消任务时是否保留已下载部分。
  • 退出程序时如果还有下载中的任务，提示“下次启动可以接着下载”。

测试

用本地模拟服务器覆盖：支持 / 不支持 Range、ETag 变化、Content-Range 起点不符、416、下载中途断开、进程被强制结束后重启恢复、直链过期后同大小与不同大小两种情况、m3u8 部分分片已完成后恢复。

6. 网络与下载源

按网站分流

国内平台走海外代理时，经常返回不同内容或直接拦截；YouTube、Pornhub、Pixiv 在国内又必须走代理。所以不能只设一个全局代理。

  • 三种出口：直连、系统代理（自动读取 Windows / macOS 的系统代理设置）、自定义代理（HTTP / SOCKS5，可存多个）。
  • 按网站的规则表：预置“抖音、快手、小红书、B站、微博等国内平台 → 直连”，“YouTube、Pornhub、Pixiv、X、Instagram、Facebook、Twitch → 系统代理”；其他网站使用默认出口。用户可以按域名增删规则。
  • 规则对所有环节生效：原生解析、下载引擎、yt-dlp（通过 --proxy 传入）、直播录制、订阅检查都用同一套规则。
  • 连通性测试：设置页对每条规则一键测试，显示延迟或失败原因（代理连不上 / 网站不可达 / 被拦截）。
  • 错误提示联动：遇到“地区限制”“连接超时”时，提示检查这个网站的代理规则，并给出跳转按钮。

国内可用的下载源

yt-dlp、ffmpeg 和程序自身的更新包默认都在 GitHub，国内经常很慢或下载失败。

  • 维护一份带签名的“组件清单”，列出每个组件的版本、各系统的下载地址（GitHub + 备用镜像）和 SHA-256。程序按清单测速选择最快的地址，下载后校验 SHA-256，不一致就丢弃。
  • 备用镜像放在国内可访问的对象存储或 CDN 上，由发布流程自动同步。
  • 支持“手动选择本地文件导入”：用户从别处下好 yt-dlp / ffmpeg 后直接指定文件，程序校验版本后使用。
  • 设置页显示各组件版本、来源和更新时间，可单独更新或回退到上一个版本（yt-dlp 新版偶尔会出问题）。

7. 短剧与剧集

  • 可以做的：网页端能播放的短剧（多数用 m3u8 播放）、yt-dlp 支持的剧集页、B站等平台上的短剧合集。
  • 做不了的：只能在手机 App 里观看、内容加密的短剧（如部分短剧 App 的付费剧集）。遇到这类内容时明确提示“内容已加密，不支持下载”，不尝试破解。
  • 按集批量下载：解析剧集页后列出全部集数，支持“全选 / 第 1–80 集 / 只下未下载的集”，按集数顺序下载。
  • 命名：新增模板变量 {series}（剧名）、{episode}（集数，可补零到两位或三位）、{index}（列表序号）、{season}；默认保存为 剧名/第01集.mp4。
  • 追更：剧集可以直接加入订阅（见第 8 节），更新后自动下载新集。
  • m3u8 细节：分片并发下载、AES-128 解密、广告分片过滤（时长或域名明显不同的分片可选跳过）、合并后用 ffmpeg 转为 MP4 并修正时间戳。

8. 订阅与追更

关注某个频道、UP主、画师、合集或剧集，定期检查，有新内容自动下载。

可以订阅的对象

  • YouTube 频道 / 播放列表、B站 UP主空间 / 合集 / 收藏夹、Pixiv 画师、Pornhub 用户、短剧剧集，以及 yt-dlp 能列出条目的任意列表页。
  • 抖音用户主页：作品列表接口需要签名参数，难度和风险最高。计划用程序内置的隐藏浏览器窗口打开主页读取作品列表，失败时提示需要登录。

检查与下载

  • 检查频率：每个订阅单独设置，最短 1 小时，默认 6 小时；在设定时间上随机加减几分钟，避免固定节奏被识别。每次只拉取最新的一页（例如最近 30 条）。
  • 首次订阅：选择“只下载以后的新内容”（默认）、“下载最近 N 条”或“下载全部”。
  • 去重：每个订阅记录已见过的条目（下载档案），已下载、已忽略的不会重复下载；与媒体库的已下载记录互通。
  • 过滤条件：标题包含 / 排除关键词、时长范围、发布时间、类型（视频 / 图集 / 直播回放）。
  • 每个订阅独立设置：画质预设、保存目录、命名模板、使用哪个登录账号、网络规则。
  • 后台运行：程序在托盘运行时检查；可设开机自启。程序关闭期间错过的检查，启动后补做一次。
  • 异常处理：连续 3 次检查失败（例如 Cookie 过期、频道被删）自动暂停该订阅并通知，给出修复入口。

界面

  • 新增“订阅”页面：每个订阅显示头像、名称、平台、上次检查时间、新内容数量、状态；支持“立即检查”“暂停”“编辑”。
  • 订阅详情：已下载 / 待下载 / 已忽略三个列表，可手动补下或忽略某条。
  • 有新内容下载完成时发系统通知（可按订阅关闭）。

限制

  • 默认关闭，首次开启时说明用途和封号风险。
  • 每个网站的检查和下载都受第 11 节中的“按网站限流”约束；单次检查最多自动下载 N 条（默认 20），超出的进入待下载列表等用户确认。

技术要点

  • 列表获取：原生插件实现各平台的列表接口；yt-dlp 用 --flat-playlist 只取条目信息，不逐条解析。
  • 数据表：subscriptions（订阅设置、上次检查时间、状态）、subscription_items（条目 ID、标题、发布时间、状态）。

9. 直播录制

添加直播间后自动监控，开播即录制，下播自动结束。参考产品：录播姬（BililiveRecorder，B站专用）、DouyinLiveRecorder（多平台）。

支持的平台

  • 原生实现：B站、抖音、快手、斗鱼、虎牙。各平台获取直播流地址的方式不同，斗鱼、虎牙需要计算签名参数，维护成本较高。
  • 通过 yt-dlp：YouTube 直播、Twitch 等 yt-dlp 支持的直播。

录制

  • 不转码：直接保存直播流（FLV 或 HLS 分片），CPU 占用低；录制格式用 FLV 或 TS，因为程序崩溃或断电时 MP4 会损坏，FLV / TS 已录部分仍可播放。
  • 自动分段：按时长（默认每 1 小时）或大小切分文件。
  • 断流重连：网络或推流中断时自动重连，同一场直播继续录到新分段；直播间恢复后不丢内容。
  • 录完处理：可选用 ffmpeg 无损转为 MP4、修正时间戳、合并同一场的分段。
  • 画质：每个直播间可选画质（原画 / 蓝光 / 超清等，按平台提供的档位）。
  • 弹幕：B站、抖音、斗鱼、虎牙的弹幕同步保存为 XML，可转 ASS 字幕（阶段内的 P2）。
  • 命名：默认 主播名/2026-10-04_直播标题_01.flv。

监控与资源

  • 开播检测间隔默认 60 秒（每个平台有下限），检测请求受按网站限流约束。
  • 同时录制数量上限可设；录制前和录制中检查磁盘空间，低于阈值时停止录制并通知。
  • 可选按天数自动清理旧录像（默认关闭）。
  • 开播、录制开始、录制异常、下播都可发通知。

界面

  • 新增“直播”页面：直播间卡片显示封面、主播、状态（未开播 / 录制中 / 异常）、已录时长和大小；支持“立即录制”“停止”“暂停监控”。
  • 录制中可打开所在文件夹，或用系统播放器查看正在录制的文件。

边界

  • 仅供个人留存，不做转推、二次直播。
  • 付费直播、加密直播不支持。

10. 手机发链接到电脑

短视频链接大多在手机上复制。电脑端开启“手机发送”后，手机扫码打开局域网网页，粘贴链接即可让电脑开始下载，不经过任何外部服务器。

流程

  • 电脑端开启后，在局域网地址上启动一个小型网页服务（随机端口），界面显示二维码。
  • 手机扫码打开网页：一个粘贴框、一个“发送”按钮，下方显示最近发送的链接及其状态（解析中 / 下载中 / 已完成 / 失败）。
  • 电脑收到后按正常流程解析和下载；“识别后自动下载”关闭时，在电脑上弹出迷你窗确认。

手机上的快捷方式

  • iPhone：提供“快捷指令”模板，加入系统分享菜单后，在抖音等 App 里点“分享 → 发送到清影”即可，不用打开网页。
  • Android：提供配置说明，用 HTTP Shortcuts 等工具加入分享菜单。
  • 局域网网页是 HTTP 页面，浏览器不允许它直接读取剪贴板，所以网页上需要用户手动长按粘贴；快捷方式没有这个限制。

安全

  • 默认关闭；只监听局域网地址，拒绝来自公网的请求。
  • 二维码里带随机生成的访问令牌；新设备第一次发送时，电脑端弹窗确认配对，之后可在设置里查看和撤销已配对的设备。
  • 网页只能“发送链接”和“查看自己发送的任务状态”，不能浏览或下载电脑上的文件。
  • 限制请求大小和频率；关闭功能时立即停止服务。
  • 首次开启时 Windows 会弹出防火墙提示，界面上提前说明。
  • 不在同一网络时不支持（需要服务器中转，不在本期范围）。

12. 平台细分

分三层：原生插件平台（自己写解析，体验最好）、重点站点（走 yt-dlp，但界面和 Cookie 引导单独优化）、yt-dlp 支持的全部站点（自动兜底）。

13. 分阶段计划

按 1 名开发估算，约 24–27 周（6 个月左右）。每阶段单独开合并请求，前一阶段合并后再开始下一阶段。建议阶段 4 完成后发布 1.0（通用下载器），订阅追更为 1.1，直播录制为 1.2。

阶段 1 · 2–3 周

加固现有程序

  • 五个平台真实链接实测，用真实响应替换测试样本；加入“录制样本”调试功能
  • 修复审查中的问题：重复入队、速度虚高、暂停延迟、Windows 文件名、快捷键错误提示、同步命令
  • 断点续传加固：任务存数据库并在启动时恢复；If-Range 与 Content-Range 校验；直链过期后保留已下载部分；暂停立即生效
  • 日志文件与“复制诊断信息”；错误分类的第一版
  • Cookie 按条存储、按域名匹配（不再发给 CDN）、加密存储；cookies.txt 导入
验收：审查表里的“高”“中”级问题全部关闭（数据模型那项留给阶段 2）；下载到一半强制结束程序，重启后能从断点继续；每个平台 10 条真实链接解析成功率不低于 90%。
阶段 2 · 4 周

通用内核

  • 新数据模型（多格式、播放列表、剧集、按资源的请求头），现有解析器迁移过去
  • 多步骤任务（下载 → 合并 → 后处理），每一步都可恢复
  • 下载引擎抽象：HTTP 单线程、分段多线程（按段续传）
  • 网络分流规则、代理、限速；按网站限制并发和频率
  • 磁盘空间检查、临时目录、文件冲突策略
  • Cookie 多账号、登录状态检测、过期提醒、“需要登录”时的引导
验收：现有功能不退化；可选清晰度；国内平台直连、海外网站走代理同时工作。
阶段 3 · 4–5 周

通用下载能力

  • 组件清单、国内镜像、yt-dlp 和 ffmpeg 的按需下载、校验、更新与回退、手动导入
  • yt-dlp 解析接入（调用安全措施同步落实），原生失败时自动兜底
  • m3u8 下载器（按分片续传、广告分片过滤）、DASH 分轨续传与合并、只下音频
  • 画质预设与 H.264 优先；短剧按集批量下载与剧集命名
  • 通用网页嗅探；B站 DASH 高清
  • yt-dlp 的临时 cookies 文件与 Cookie 回写
  • Pixiv 原生插件（作品、多图、动图合成、R-18 登录）
  • 从 yt-dlp --list-extractors 生成“支持的网站”页面
验收：YouTube、Pornhub、B站 1080P、Pixiv 多图和动图、典型 m3u8 短剧页都能正常下载；在国内网络下首次使用能顺利装好 yt-dlp 和 ffmpeg。
阶段 4 · 3–4 周

体验细节 → 发布 1.0

  • 格式选择界面、合集 / 剧集勾选、拖拽导入、剪贴板白名单
  • 手机发链接到电脑（局域网服务、配对、iPhone 快捷指令模板）
  • 媒体库封面缓存、筛选、重新下载；整理功能（自动建文件夹、元数据、信息文件、NFO）
  • 下载完成动作、队列排序、定时下载、阻止休眠
  • 大量数据时的性能（虚拟滚动、索引）；平台健康检查；便携版
验收：手机分享链接到电脑 5 秒内开始下载；1000 条任务时界面流畅。
阶段 5 · 3 周

订阅与追更 → 1.1

  • 订阅数据表、检查调度（随机间隔、补检、按网站限流）、下载档案去重
  • 各平台列表获取：yt-dlp 平铺列表、B站 / Pixiv 原生接口、抖音主页（隐藏浏览器窗口）
  • 过滤条件、首次订阅策略、单次下载上限、失败自动暂停
  • “订阅”页面与通知；开机自启
验收：订阅 10 个不同平台的对象，连续运行 3 天，新内容全部按时下载且没有重复。
阶段 6 · 4–5 周

直播录制 → 1.2

  • 开播检测与直播流获取：B站、抖音、快手、斗鱼、虎牙原生实现；其他走 yt-dlp
  • 录制引擎：FLV / HLS 直接保存、自动分段、断流重连、磁盘空间保护
  • 录完处理（转 MP4、修正时间戳、合并分段）
  • “直播”页面、通知；弹幕录制（P2）
验收：同时录制 3 个直播间各 6 小时，中途断网 1 分钟后自动恢复，文件都能正常播放。
阶段 7 · 3 周

生态与分发

  • 浏览器扩展：一键发送链接 + 一键同步 Cookie，clearclip:// 唤起（YouTube 登录依赖这一项，可在阶段 3 之后提前穿插）
  • 签名自动更新（走国内镜像）、Windows 代码签名、macOS 公证
  • 上架 winget、Scoop、Homebrew；准备国内下载地址
  • 解析规则远程更新、多语言、字幕弹幕、图集合成视频

主要风险

  • 平台风控和改版：通用化不会消除这一点。靠日志、健康检查、样本录制和规则更新尽快发现和修复。
  • 签名参数：抖音主页列表、斗鱼和虎牙直播流都需要计算签名，平台调整后要尽快跟进；订阅和直播是最容易失效的部分。
  • 外部程序：yt-dlp 和 ffmpeg 的版本差异、杀毒软件误报都要处理；镜像需要持续同步。
  • 账号风险：用登录 Cookie 大量下载或频繁检查订阅可能导致账号被标记或封禁；程序按网站限流并明确提示。
  • 后台资源：订阅检查和直播录制要求程序常驻，需控制内存、网络和磁盘占用。
  • 合规：保持免责声明；不做 DRM 破解、会员内容绕过、直播转推；批量采集默认关闭。
  • 体积：程序本体约 10 MB；加上 yt-dlp 和 ffmpeg 后磁盘占用约 100–150 MB，直播录像另计。

14. 质量与维护

每阶段的验收方式

  • 每个阶段的“验收”写在上面的计划里，用真实链接、真实直播间和模拟服务器两类测试共同验证；合并前在 Windows、macOS、Linux 各跑一遍主要流程。
  • CI 继续跑格式检查、代码检查、单元测试、前端构建；新增模拟服务器上的断点续传、m3u8、订阅调度测试。

解析器维护流程

  • 录制样本：程序里的调试功能，把出问题链接的页面和接口响应去掉 Cookie 等隐私信息后保存，直接作为回归测试样本。
  • 定期巡检：每天用一组真实链接和直播间自动检查各平台。GitHub 的服务器在海外，国内平台的巡检放在国内机器上运行（自建运行器或定时任务），结果汇总到一个看板。
  • 快速修复：巡检失败时先尝试远程规则更新；需要改代码的问题发布补丁版本，通过签名自动更新推送。

分发

  • winget、Scoop、Homebrew；Windows 便携版 zip。
  • Windows 代码签名减少“未知发布者”拦截；macOS 签名与公证。
